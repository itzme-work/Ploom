# Репетиция 0.1.0 → 0.1.1-test

Для Windows x64 доступен [мастер PowerShell без SDK](windows-rehearsal.md). Ниже сохранён вариант для Bash.
Используйте чистый профиль Windows и выделенный Android без существующей установки Ploom. Обе версии используют work.itzme.ploom и одно имя продукта. Конфликт с подписью ранее установленного клиента требует другого тестового устройства или профиля. Удаление существующего приложения может уничтожить данные.

## Действия владельца

1. Подготовьте личный ПК с зашифрованным диском. На Windows удобно использовать WSL с Git, Node 22+, JDK 17, Python 3 и GitHub CLI. Выполните `gh auth login --hostname github.com`, выберите GitHub.com → HTTPS → вход через браузер. Работайте с проверенной чистой копией native-completion из Linux home, со своим личным аккаунтом GitHub.
2. Для сквозного теста с двух устройств нужен доступный им HTTPS-адрес. Клиенты запрашивают метаданные и пакет по сети, а GitHub Actions Artifacts требуют авторизации GitHub. Бесплатный вариант для личной лаборатории — Tailscale Personal и **Serve** на компьютере владельца. Подключите ПК и телефон к одному личному tailnet. В консоли Tailscale откройте DNS, включите MagicDNS и HTTPS Certificates. Скопируйте полное DNS-имя ПК вида `device.name.ts.net` из Machines. Ограничьте доступ в tailnet тестовыми устройствами. Имя HTTPS-узла будет видно в журналах прозрачности сертификатов. Для этой процедуры используется Serve с доступом внутри tailnet. Функция Funnel открывает публичный доступ и для репетиции не подходит. [Инструкция Tailscale Serve](https://tailscale.com/kb/1242/tailscale-serve)
3. В корне репозитория запустите `bash scripts/rehearse.sh`. Введите DNS-имя и подтвердите имя личного private-репозитория. Мастер создаёт или использует выделенную копию **Ploom-rehearsal**. Используйте её только для проверенного кода Ploom без сторонних участников с правом записи. Мастер создаёт тестовые ключи локально, повторно использует их при следующем запуске, настраивает GitHub Actions Secrets через stdin и запускает четыре сборки. Задайте непустые разные пароли для Android и Tauri. По запросу мастера сохраните зашифрованную резервную копию каталога ключей и проверьте её чтение. Подсказки GitHub CLI для двух паролей требуют тех же значений. Секреты доступны процессу подписи на GitHub runner во время сборки. Производственные ключи для этой репетиции не используются.
4. На GitHub откройте **свой приватный Ploom-rehearsal → Actions → Signed test packages → последний запуск → Summary → Artifacts**. Если Actions отключены, нажмите **Actions → Enable workflows**, затем **Signed test packages → Run workflow → native-completion → Run workflow**. Скачайте `rehearsal-0.1.0-Windows`, `rehearsal-0.1.0-Linux` (внутри Android APK) и `private-rehearsal-site`. Остальные два пакета уже включены в стенд. Срок хранения подписанных тестовых артефактов — три дня. В публичном Ploom подпись заблокирована проверкой видимости репозитория.
5. Распакуйте `private-rehearsal-site` в **отдельный пустой каталог**. В первом терминале выполните `python3 scripts/serve-rehearsal.py /путь/к/распакованному-сайту`. Во втором на том же компьютере — `tailscale serve --bg http://127.0.0.1:8765`. На телефоне откройте `https://ВАШ-ХОСТ/releases.json` и убедитесь, что отображается тег v0.1.1-test. Используйте этот выделенный узел только для репетиции. После проверки остановите Python и выполните `tailscale serve reset` на этом узле. Для обычного теста экранов стенд не нужен.

Мастер сохраняет тестовые ключи вне Git в `$XDG_DATA_HOME/ploom-rehearsal` или `~/.local/share/ploom-rehearsal`. Файлы закрытых ключей не входят в стенд. GitHub-репозиторий и настройки Actions должен контролировать лично владелец. Для первого официального выпуска выполните отдельную локальную настройку production-ключей после приёмки обеих ОС.

## Протокол приёмки на каждой ОС

1. Установите тестовую 0.1.0, зафиксируйте версию, выберите Beta, ASCII, русский язык и янтарный акцент. Перезапустите приложение и проверьте значения. Сделайте снимок тестовой ВМ или резервную копию профиля до обновления.
2. Сначала проверьте отказ. В отдельной попытке подмените копию Windows-подписи или измените подписанный APK на стенде. Запустите обновление. Установка должна прерваться, прежняя версия и настройки должны открываться. Верните оригиналы. Аналогично проверьте обрыв сети.
3. В Summary проверьте зелёный шаг **Verify both package identities and signatures**. CI сравнивает сертификаты двух APK, имя пакета, версии и коды 100 → 101, проверяет ELF/ZIP-выравнивание и обе подписи Windows с подписанной версией. На Android Нажмите обновление, отмените системный диалог и убедитесь, что по-прежнему открывается 0.1.0. Повторите и подтвердите установку в Android. При первом запросе разрешите установку из Ploom только на тестовом устройстве и повторите действие.
4. На Windows нажмите обновление. После перезапуска проверьте версию в Ploom и в свойствах установленного продукта. На Android откройте приложение с ярлыка. На обеих платформах версия должна стать 0.1.1-test, настройки и канал должны сохраниться. Наличие только загруженного файла или открытого системного диалога успехом не считается.
5. После успешного перехода верните в тестовые метаданные 0.1.0. Повторная проверка не должна предлагать понижение. Зафиксируйте статус, версии до и после, отпечатки, настройки и результат каждой попытки. Будущие подписки проверить в этой версии невозможно.

При сбое прекратите раздачу проблемного пакета, сохраните журнал и текущие данные приложения. Для повторения верните снимок изолированного профиля или ВМ. В рабочей среде путь восстановления — исправленная сборка с более высокой версией и той же доверенной подписью. Стабильный выпуск требует отдельного решения владельца после успешного теста обеих платформ.
