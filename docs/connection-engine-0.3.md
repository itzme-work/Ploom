## Условия распространения

sing-box распространяется по GPL-3.0-or-later. Upstream также запрещает производным работам использовать имя или подразумевать связь с приложением без разрешения. При прямом связывании через libbox план выпуска должен предусматривать GPL-совместимое распространение комбинированной программы, доступ к полному соответствующему исходному коду точной поставки, скриптам сборки, изменениям и применимым сведениям для установки. Уведомления Apache-2.0 и авторство исходных файлов Ploom сохраняются. Владелец согласовал условия комбинированной поставки. До распространения нужны инвентаризация транзитивных лицензий и проверка комплекта исходников. Самостоятельный запуск инструментов в стенде не меняет лицензию репозитория. [Лицензия выбранной версии](https://github.com/SagerNet/sing-box/blob/c005f35300ce76427dc285481ec5695f5b179cd2/LICENSE)

## Испытание передачи TCP

На Linux x64 все три движка последовательно передали один и тот же массив случайных данных объёмом 4 МиБ. Клиент стенда открывает SOCKS5 на loopback, движок связывается с фиксированным HTTP CONNECT-сервером, тот передаёт запрос единственному разрешённому локальному серверу. Проверяются все байты ответа и число обращений к посреднику. Загрузки сверяются с закреплёнными SHA-256 до запуска. Команда для CI — bash scripts/engine-lab/run.sh.

| Движок | Старт до запроса, мс | Приём, МиБ/с | Пиковая RSS, КиБ | CPU, с | Файл Linux, байт |
|---|---:|---:|---:|---:|---:|
| sing-box | 62,5 | 186,0 | 55316 | 0,07 | 81416421 |
| Xray | 17,7 | 380,7 | 30512 | 0,02 | 35434620 |
| Mihomo | 27,5 | 386,6 | 42140 | 0,03 | 61948030 |

Медианы трёх последовательных успешных прогонов по каждому столбцу. Малый объём и локальная сеть дают большой разброс. В предварительном прогоне Mihomo один раз закрыл поток до получения данных. Размер файла Linux не определяет размер будущего APK или NSIS.

| Режим или протокол | Подтверждение в Ploom |
|---|---|
| HTTP CONNECT outbound через локальный SOCKS5 inbound | Частично. Реальная передача только на Linux в стенде |
| SOCKS5 outbound, HTTPS proxy, VLESS/REALITY/Vision, VMess, Trojan, Shadowsocks, Hysteria2, TUIC, WireGuard | Требуют проверки исходящего соединения для каждой комбинации |
| Android VpnService, Windows TUN и System Proxy | Не реализованы в этой ветке |
| IPv6, UDP, DNS через туннель, восстановление маршрутов, Kill Switch | Требуют отдельных системных испытаний |

Статус в интерфейсе остаётся отключённым. Следующие этапы требуют передачи TUN-дескриптора и защиты сокетов Android, управления привилегиями Windows, привязки статистики к активной сессии и испытаний восстановления после сбоя. Редактор политик остаётся задачей 0.4.0.

## Состояние интеграции в PR № 15

Таблица выше фиксирует исходный сравнительный эксперимент. Последующие испытания sing-box 1.14.4 используют пару клиент/провайдер и одноразовые учётные данные. На Linux получен побайтовый ответ по HTTP, HTTPS, SOCKS5, Shadowsocks (AES-256-GCM), Trojan/TLS, VMess/TLS, VLESS/TLS, Hysteria2, TUIC и VLESS REALITY/Vision. Через Shadowsocks выполнен обмен DNS-пакетами UDP с адресатами IPv4 и IPv6. Эти испытания можно повторить командой `bash scripts/engine-lab/run.sh`. Они используют лабораторные конфигурации ядра. Нативный преобразователь Ploom отклоняет неизвестные поля; набор импортируемых форматов шире набора форматов подключения.

В workflow **Android libbox ARM64** собираются отдельные debug-пакеты с ядром. Android запрашивает системное согласие при подключении, создаёт TUN и вызывает protect для исходящих сокетов. Маршруты охватывают обе версии IP, запросы на порт 53 направляются резолверу ядра, резолвер Quad9 доступен по DNS-over-TLS через провайдера. Разрешение на подключение к частному IP действует на одно выбранное сочетание адреса и порта. Камера запрашивается отдельной кнопкой сканера. Полученный текст поступает в предпросмотр.

Windows Local Proxy использует смешанный HTTP/SOCKS-вход на loopback. Хеш исполняемого файла вычисляется при сборке клиента и проверяется перед запуском, JSON подаётся через stdin. В режиме System Proxy отдельный пользовательский процесс восстанавливает первоначальные параметры при закрытии канала родительского процесса. После перезагрузки оставшаяся запись восстановления обрабатывается при запуске Ploom. Настроенный PAC блокирует этот режим. Windows TUN, полный Kill Switch и его аварийное восстановление пока не подтверждены. Официальная бинарная поставка Wintun имеет отдельные условия использования разрешённого API и распространения DLL; её нельзя самостоятельно перелицензировать по GPL.

### Создание исходного комплекта и SBOM

Владелец может открыть **GitHub → Actions → Android libbox ARM64**, выбрать запуск PR и скачать артефакт. Для сборки используются JDK 17, Go 1.26.10, Android NDK 27.2.12479018, исходный коммит c005f35300ce76427dc285481ec5695f5b179cd2 и проверка SHA-256 исходного архива. Точная команда gomobile, теги и изменения libbox находятся в scripts/libbox. Патч выключает запись configuration.json из процесса libbox, дополнение экспортирует агрегированные счётчики. В Linux-среде с этими SDK команда `bash scripts/libbox/build.sh OUTPUT` создаёт AAR.

Комплект CI включает исходники Ploom, архив upstream, исходники зависимостей Go, Java bindings, данные линкера, CycloneDX для Go и для production npm-зависимостей. Генератор notices.py сопоставляет файлы лицензий с фактически связанными Go-модулями. Полный лицензионный аудит Rust, Maven, NDK и Windows и сверка соответствующего исходного кода с обоими финальными установщиками остаются условиями выпуска. Карточка версии является идентификатором тестовой ветки. Присутствие APK/NSIS в артефактах само по себе не подтверждает прохождение трафика на устройствах.

Проверка Windows-зависимостей выявила, что внутренний Go-пакет sing-tun содержит директиву go:embed для Wintun 0.14.1. Бинарник из закреплённой ревизии имеет тот же SHA-256, что amd64 DLL из официального архива WireGuard. Лицензия DLL вложена в LICENSES/Wintun-0.14.1.txt; MIT относится к обвязке. Для решения о публичной поставке следует оценить условия распространения именно встроенной копии и полный комплект соответствующих исходников. [Исходник загрузчика](https://github.com/SagerNet/sing-tun/blob/040db71fcd33/internal/wintun/dll_windows_amd64.go) · [Официальный комплект](https://www.wintun.net/builds/wintun-0.14.1.zip)

На коммите f2c6f9a Windows runner установил NSIS поверх подписанной 0.2.0, восстановил зашифрованную библиотеку и проверил личный выбор сервера и настройки. При запуске установленного Ploom реальные данные прошли через Local Proxy на контролируемый HTTP CONNECT-сервер. После принудительного закрытия Ploom локальный порт освободился. Отдельный тест запустил установленное ядро с правами runner, направил только контрольный адрес /32 в TUN и проверил исчезновение маршрута после остановки процесса. Получение полномочий из обычной пользовательской сессии этим тестом не покрывается. [Журнал Windows](https://github.com/itzme-work/Ploom/actions/runs/45582803912/job/139096797563)

В сборке для ревью Windows x64 используется отдельная официальная Wintun DLL. Скрипт scripts/windows-core/prepare.py сверяет SHA-256 архива, DLL и двух исходных файлов sing-tun перед сборкой с Go overlay. Лицензия Wintun сохраняется рядом с DLL. Загрузчик проверяет SHA-256 под открытым файловым дескриптором, запрещающим замену файла, и передаёт абсолютный путь системному загрузчику Windows. CI отдельно проверяет отсутствие встроенной копии DLL в EXE. Это изменение касается упаковки Wintun. Общий аудит компонентов и проверка установленной сборки продолжаются.
